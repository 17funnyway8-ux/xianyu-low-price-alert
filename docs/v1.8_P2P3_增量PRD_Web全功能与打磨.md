### 2.3 业务逻辑核对结论（Web 调用 vs 桌面 monitor/storage 行为）

| 业务点 | 结论 | 证据 |
| --- | --- | --- |
| 去重（notified 标志） | ✅ Web 复用核心 `Monitor.run_once`，去重语义与桌面一致 | monitor_service.py 直接构造 `Monitor(config, fetcher, storage, notifiers)` |
| 「新商品」判定（meta `prev_ids`） | ✅ 核心逻辑，Web 不干预 | 同上 |
| 价格阈值严格 `<` | ✅ 核心判定，Web 不干预 | 同上 |
| Cookie 池轮换（resolve_cookie_for_round） | ✅ 核心逻辑在 monitor 内自动执行；**但 Web 无 UI 管理池，只能靠 config.yaml 手工维护** | cookie.py:263；Web 表单往返保留 `cookie_pool`（monitor_service.py:287-288） |
| 售出/黑名单互斥语义 | ✅ `list_notified` 自动排除黑名单（v3.6）+ 默认排除已售出（v3.7）；Web records 走同一 `list_notified`；Web `POST /records/{id}/blacklist` 先查 keyword 再 `add_blacklist`，与 GUI `blacklist_alert_row` 等价 | storage.py:274-313；api.py:280-302 |
| 售出标记（跨关键词全局） | ✅ Web `mark_sold_out_by_id` 与 GUI `on_mark_sold_selected` 同函数 | api.py:267-277 |
| monitor 运行中手动单轮 | ✅ 409 拒绝（与 GUI「请先停止」一致） | api.py:166-172 / monitor_service.py:506-508 |
| 配置保存 → 热重启 | ✅ `apply_config`：校验→停止→写盘→重载→重启（若原在运行）；测试 `test_apply_config_hot_restart` 覆盖 | monitor_service.py:574-607 |
| config mtime 外部重载 | ✅ `_check_config_mtime` 每轮比对 + `reload_if_external_changed` 保存后立即重载；测试覆盖 | monitor_service.py:369-386 |

> **核对结论**：P1 对「核心业务逻辑」的复用是**正确且完整的**——缺的不是逻辑，而是「让用户能通过 Web 管理这些逻辑所需的数据（池/黑名单/售出状态/记录）」的**管理与交互层**。P2 需求池即由此推出。

## 3. P2 需求池（Web 全功能）

> 优先级约定：**P0 = Must have（业务闭环必需）**；**P1 = Should have（体验完整）**；**P2 = Nice to have（锦上添花）**。

### P2-P0（Must have，业务闭环）

#### 需求 P2-01：Cookie 池管理（对齐 GUI `on_manage_cookies`，§3.2 #7/#9）
- **must** 提供 `GET /api/cookie/pool`：返回脱敏池列表（name / enabled / health state+reason / expire 时间，`mask_cookie` 脱敏，绝不出明文）。
- **must** 提供 `POST /api/cookie/pool` 操作（action 字段驱动）：`add`（命名+粘贴，缺 `_m_h5_tk` 时二次确认）、`update`（改名/换 Cookie）、`delete`（二次确认）、`toggle`（启停）、`set_default`（写入单值 `monitor.cookies` + 加密落盘 + mtime 重载）、`refresh_selected`（校验非 ok 拒绝，v1.8 C15 语义）、`auto_disable_expired`（检测 expired/no_token/missing/invalid_encrypt → 批量停用，保留条目）。
- **must** 前端「Cookie 管理」弹窗：列表（名称/状态/有效性/过期时间）+ 操作按钮 + 帮助文案（容器内粘贴版）+ 「检测全部」。
- **must** 保存后触发配置重载，运行中 monitor 下一轮换用新池（复用 `reload_if_external_changed`）。
- **should** 池为空时回退单值（与 `resolve_cookie_for_round` 语义一致，提示用户）。
- 验收：见 §5 P2-01。

#### 需求 P2-02：黑名单管理（查看/恢复，对齐 GUI `on_manage_blacklist`，§3.2 #17）
- **must** 提供 `GET /api/blacklist?limit=`：返回 `(product_id, keyword, reason, created_at)` 列表。
- **must** 提供 `POST /api/blacklist/{product_id}/restore`：`remove_blacklist` 移出（幂等）。
- **must** 前端「黑名单管理」弹窗：列表 + 「恢复选中」+ 关闭；恢复后日志记录 + 刷新记录表。
- **should** 「加入黑名单」操作支持填写原因（复用现有 `POST /records/{id}/blacklist` body.reason，前端加输入框）。
- 验收：见 §5 P2-02。

#### 需求 P2-03：校验在架 / 批量售出标记（对齐 GUI `on_check_on_shelf`，§3.2 #16）
- **must** 提供 `POST /api/records/check_shelf`：接收 product_id 列表（上限 `SOLD_CHECK_MAX_ITEMS=30`，对齐 GUI）；monitor 运行时返回 409（GUI 语义：先停止）；fetcher 非 mtop 返回 400。
- **must** 后台逐条 `check_item_status(pid, timeout=12.0)`，**两次请求间限速 `SOLD_CHECK_INTERVAL=1.5s`**（对齐 GUI，防风控）；判定 False → `mark_sold_out_by_id(pid, reason=SOLD_REASON_DETAIL)`。
- **must** 全程进度写日志（环形缓冲 + SSE 可见）：开始/逐条结果（在线/已下架/异常）/完成统计。
- **should** 支持中止（stop 信号中断批处理）；单条失败不中断批量（记 WARNING 继续）。
- 验收：见 §5 P2-03。

#### 需求 P2-04：售出撤销（恢复在架，对齐 GUI 再点一次语义）
- **must** 提供 `POST /api/records/{id}/unmark`：`unmark_sold_out(product_id)` 恢复在架（幂等）。
- **must** 前端：`include_sold=True` 时已售出行灰显 + 按钮文案变「恢复在架」（对齐 GUI 灰色 + 再点恢复）；隐藏售出时该行不显示。
- **should** 标记/撤销售出后日志记录 + 刷新记录表。
- 验收：见 §5 P2-04。

#### 需求 P2-05：清空去重记录（对齐 GUI `on_clear_records`，§3.2 #18）
- **must** 提供 `POST /api/records/clear`：`storage.clear_all()`（product + meta；**不清 blacklist**，对齐 v3.6 语义）；monitor 运行时返回 409（先停止）。
- **must** 前端按钮 + 二次确认弹窗（文案明确「清空后已提醒商品会重新视为新商品，可能重复提醒，不可撤销」）。
- **should** 返回删除条数并展示。
- 验收：见 §5 P2-05。

#### 需求 P2-06：关键词更新（改词/改价）与过滤词弹窗（§3.2 #1/#2）
- **must** 关键词行支持「编辑」：修改 keyword / max_price（复用 `validate_keyword_entry` / 重名校验），替代「删除重建」。
- **must** 过滤词弹窗替换 `prompt()`：排除词 / 必含词 多行输入 + 保存/取消 + 当前关键词名展示（对齐 GUI `_open_filter_dialog` 交互）。
- **should** 弹窗内校验（空关键词拒绝、非法价格拒绝）并有明确错误提示。
- 验收：见 §5 P2-06。

#### 需求 P2-07：配置热重启完整性核对（§6 P2 行）
- **must** 保存配置后：`round_count`/`notified_count`/`last_round_at` 保留不清零；monitor 原运行 → 重启后状态条正确（running=true）；原停止 → 保持停止。
- **must** 保存失败（ConfigError）时不落盘、monitor 状态不变、前端收到 400 + 中文原因。
- **should** 新增测试：保存热重启后 status 完整性（`test_apply_config_preserves_counters` 等）。
- 验收：见 §5 P2-07。

## 4. P3 需求池（打磨）

> 优先级约定同 P2。**注意**：compose 的 restart / healthcheck / TZ / logging / 资源限制在 P1 已齐备（见 §6 现状核对），P3 仅补认证接入与可选加固。

### P3-P0

#### 需求 P3-01：XY_WEB_TOKEN 认证（§5.4 / §6 P3 行）
- **must** `web/api.py` 增加 FastAPI 依赖：当环境变量 `XY_WEB_TOKEN` 非空时，除 `/healthz` 与静态资源（`/static/*`、`/`）外所有 API 要求 `Authorization: Bearer <token>`；未携带/错误返回 401 JSON（`{"ok":false,"message":"未认证或 token 错误"}`）。
- **must** 前端：首次访问若 401 → 弹出 token 输入（或独立登录遮罩）→ 校验通过存 `localStorage`；`api()` 封装统一附带 `Authorization` 头；收到 401 时清 token 并重新引导输入。
- **must** 不设 token 时行为与现在完全一致（兼容本机默认 127.0.0.1 场景）。
- **should** token 校验用常数时间比较（`secrets.compare_digest`），避免时序侧信道。
- 验收：见 §5 P3-01。

#### 需求 P3-02：README「Docker 部署」章节（§6 P3 行）
- **must** README 新增「Docker 部署」章节，覆盖：
  1) `docker compose -p xianyu-alert up -d --build` 用法 + 数据卷说明（`./xianyu-data:/app/data`）；
  2) **老数据迁移**：桌面版 `state/*.db` + `config.yaml`（含 `fernet1:` 密文）+ `secret.key` 三件套复制到卷对应位置（`secret.key` 缺失 → Cookie 需重新粘贴）；
  3) **Cookie 重登**：容器内无浏览器，Web「Cookie 管理」粘贴 / `docker exec` 跑 `cli login --cookie-string`；
  4) **备份指引**：`secret.key` + `config.yaml` + `state/xianyu_alert.db` 一起备份（SQLite `.backup` 热备命令）；
  5) 远程访问：`ports: "8080:8080"` + 设 `XY_WEB_TOKEN` + Caddy basic_auth / Tailscale 进阶；
  6) **容器内 CLI 约束**：Web 运行时不可 `once/run`（抢单实例锁返回 2），调试用 `cookie status` / `list` / `login`。
- 验收：见 §5 P3-02。

### P3-P1

#### 需求 P3-03：compose 完善核对（§6 P3 行，P1 已具备项的确认）
- **must** 确认并保留：`restart: unless-stopped` / HEALTHCHECK（HTTP `/healthz`）/ `TZ=Asia/Shanghai` / logging json-file 10m×3 / deploy 256M+0.5c（均已存在 ✅）。
- **must** 补充 `XY_WEB_TOKEN` 环境变量示例（注释，不默认启用）。
- **should** 可选 `user: "1000:1000"` 非 root（需卷属主对齐，见待确认 #6）。
- 验收：见 §5 P3-03。

#### 需求 P3-04：镜像瘦身（§6 P3 行，目标 ≤180MB）
- **must** 保持 `pip install --no-cache-dir`（已有）、不装 playwright/PySide6/tkinter（已有）。
- **must** 实测并记录镜像体积（`docker images` 后验证 ≤ ~180MB）；若超限：多阶段构建（依赖层 + 运行层）、`COPY` 精简（已用 .dockerignore）、移除不必要文件。
- **should** 可选 `USER app` 非 root 加固（与 compose `user:` 二选一/对齐）。
- **should** 构建层缓存优化（requirements 先 COPY 再源码）。
- 验收：见 §5 P3-04。

#### 需求 P3-05：CI Docker job（可选，§6 P3 行「可选」）
- **should** `.github/workflows/release.yml` 增加 `build-docker` job：`actions/setup-python` + `docker/build-push-action`（buildx amd64/arm64 → GHCR），tag 对齐 release。
- **should** 仅打 tag 时触发；失败不阻断桌面发布。
- 验收：见 §5 P3-05。

## 6. 不做什么（明确排除）

| 项 | 说明 |
| --- | --- |
| 桌面快捷方式 | §3.2 #19 已标 🔴 砍；容器无桌面语义，Web 端不做 |
| playwright 容器化 | §4.1 方案③不推荐（镜像 +1GB）；保持 Web 粘贴 + 宿主机 playwright 为辅 |
| 运行中配置热替换（复杂版） | 保持「保存 → 停止 → 重建 → 重启」简单版（§2.1 决策），不做运行中热替换复杂度 |
| 多容器架构 | 保持单容器（§2.1）；不引入 worker/db 分离 |
| DPAPI 老密文迁移 | `dpapi1:` 密文跨平台不可解；代码已优雅降级「无法解密→重登」；**不做自动迁移** |
| `XY_SECRET_KEY_BASE64` 环境注入 | §5.2 方案 B 为 P2 可选增强，默认不做；需用户拍板（待确认 #8） |
| 桌面 GUI 等价物进镜像 | 不装 PySide6/tkinter（省 150MB+），Web 即 GUI |
| 通知去抖/聚合（桌面未做） | 不在本 PRD 范围（桌面版亦无，非 Web 缺口） |
