# 故障排查手册

> 本文只记录**真实发生过**的问题（含定位过程与根因），不写"可能会这样"的空话。
> 每条给出：现象 → 原因 → 处置 → 如何确认已恢复。

---

## 1. 容器起不来：日志出现「已有实例运行中」/ 无法创建单实例锁

**现象**

@@@
无法创建单实例锁文件 /app/data/state/instance.lock（[Errno 13] Permission denied）
或者：已有实例运行中（PID 1），拒绝启动
@@@

**原因**

旧版本镜像以 **root** 运行，在数据卷里留下了 @@root:root@@ 的 @@state/instance.lock@@；
而 v1.8.2 起镜像改为**非 root（uid 1000）**运行，既无法删除该文件、也无法覆盖它。

**处置**

@@@bash
# 1) 看锁文件属主（data 目录一般是你自己的用户，不需要 sudo）
ls -l <数据目录>/state/instance.lock

# 2) 删除残留锁（进程已退出时锁文件即为残留）
rm -f <数据目录>/state/instance.lock

# 3) 让容器以数据属主的身份运行（sudo 不可用时最实用的办法）
#    docker-compose.yml:
#      user: "<属主uid>:<属组gid>"      # 例如 "1005:1001"
@@@

**如何确认已恢复**：容器状态为 @@Up (healthy)@@，且 @@curl http://127.0.0.1:8899/healthz@@ 返回 @@status: ok@@。

## 2. 升级后写不进数据卷（Permission denied / 无法落盘）

**现象**：容器启动后立刻退出，或日志报无法写入 @@config.yaml@@ / @@state/*.db@@。

**原因**：镜像从 v1.8.2 起以 uid 1000 运行，而宿主数据目录属主可能是别的 uid
（NAS 上常见，如飞牛的 1005）。

**处置**：二选一

@@@bash
# 方案 A：把数据目录交给容器用户（需要 sudo）
sudo chown -R 1000:1000 <数据目录>

# 方案 B：让容器跟随数据属主（无需 sudo，推荐在 NAS 上用）
# docker-compose.yml:
#   user: "1005:1001"
@@@

## 3. 界面显示「令牌已过期」，但其实还能用（或剩余时间明显不对）

**现象**：Cookie 状态显示"已过期"或剩余时间比实际长很多（历史版本曾显示"4 小时"而真实只剩 2.5 小时），
但抓取其实正常。

**原因（v1.9.0 之前的真实缺陷）**：@@_m_h5_tk@@ 值里的 13 位时间戳是**过期时刻**，
旧实现按"签发时刻 + 固定 TTL"解读，于是**多算了一个 TTL**；更严重的是它会把
"令牌过期"直接当成"Cookie 不可用"，在配置层就把整轮抓取判死。

**处置**

1. 升级到 **v1.9.0 或更高**（分层凭据模型 + 可用性规则修正）；
2. 打开「监控配置 → Cookie」，看**分层状态**：登录态 / 会话凭据（havana，通常 30 天）/ 签名令牌 / 风控指纹；
3. 关键判断：**"签名令牌已过期"不需要重新登录** —— 下次请求服务端会下发新令牌并自动重试。

**如何确认**：分层里"登录态"为 ok 且"会话凭据"剩余数十天 → 无需扫码，直接抓取即可。

## 4. 监控停一会儿就掉登录，总要重新扫码

**现象**：抓一次就停、或夜间空闲几小时后，第二天启动报 Cookie 失效。

**原因**：mtop 令牌**只在有请求时滑动续期**；空闲超过有效期（实测约 2–4 小时）就会过期。

**处置**：v1.9.0 起有**空闲保活**（默认开启，每 30 分钟发一次极轻量请求维持会话），
与"是否在跑监控"解耦 —— 只要服务在运行就保活。

@@@bash
# 确认保活是否在跑
curl -s http://127.0.0.1:8899/api/cookie/status | python3 -m json.tool | grep -A3 keepalive
# 期望：enabled=true, thread.running=true
@@@

关闭方式：@@monitor.keepalive_enabled: false@@。

## 5. docker compose pull 卡住 / 拉不到镜像

**现象**：@@docker compose pull@@ 长时间无响应或超时。

**原因**：部分地区直连 Docker Hub（registry-1.docker.io）不稳定。

**处置**：为 Docker 配置镜像加速器（飞牛等 NAS 通常自带），或改用
[GitHub Release](https://github.com/17funnyway8-ux/xianyu-low-price-alert/releases) 的
Windows/macOS 二进制，不依赖容器。

**旁证**：本项目实测在配置了加速器的 NAS 上，镜像**21 秒**即可拉取完成。

## 6. 网页能打开，但点哪儿都没反应

**现象**：界面渲染正常，鼠标点击无响应，控制台也无报错。

**原因（v1.8.4 之前的真实缺陷）**：全屏大图遮罩声明了 @@display: flex@@，
**覆盖了 @@[hidden]@@ 的 @@display:none@@** → 隐藏状态下遮罩仍铺满屏幕并拦截全部点击。

**处置**：升级到 v1.8.4+（已修）。排查同类问题的通用手法：在控制台执行
@@document.elementFromPoint(x, y)@@ 看**实际**命中的元素是不是意料之外的覆盖层。

## 7. 某轮抓取失败，如何判断该做什么

按日志关键词对照下表处置，**不要一律去重新登录**：

| 日志关键词 | 含义 | 正确处置 |
|---|---|---|
| @@FAIL_SYS_TOKEN_EXOIRED@@ / @@TOKEN_EMPTY@@ | 令牌层问题（可自愈） | 无需操作，下次请求自动续期；持续失败再查登录态 |
| @@RGV587_ERROR@@ / 「被挤爆啦」 | 风控 | 降低频率、固定出口 IP，**不要**频繁切换网络 |
| 「登录态已失效」「请重新登录」 | 会话层问题 | 先试**免扫码刷新**（复用浏览器 profile），失败再扫码 |
| 「缺少 _m_h5_tk」 | 粘贴的 Cookie 不完整 | 重新完整复制 Cookie 请求头 |
| 「密文无法解密」 | 换了机器/用户，密钥不匹配 | 重新登录获取 Cookie |

## 8. 想彻底重来（重置数据）

@@@bash
# 停止并删除容器（数据卷保留）
docker compose -p xianyu-alert down

# 备份后清空数据（配置、数据库、浏览器 profile 都在这里）
mv <数据目录> <数据目录>.bak-$(date +%Y%m%d)
mkdir -p <数据目录>

docker compose -p xianyu-alert up -d
@@@

> 注意：@@<数据目录>@@ 里的 @@secret.key@@ 是 Cookie 加密密钥，删除后需重新登录。

## 9. 网页兜底采集解析不出来（0 条）

**现象**：走网页解析路径时这一轮 0 条，但页面在浏览器里看着正常。

**原因**：网页路径依赖平台把商品数据放在页面什么位置（内联 JSON / JSON-LD / DOM 卡片），
平台改版就可能失效 —— 这是它作为**兜底**路径的固有代价（默认的 mtop 路径不受影响）。

**处置**：看日志里那一行诊断，它会说明扫描了多少链接、各自为何被跳过：

```
[web] 网页解析 0 条（策略=dom，HTML 8231 字节）：扫描链接 42，无商品ID 38，缺标题 0，缺价格 4，重复 0，非法 0 | 多数卡片缺价格：平台可能改了价格节点，检查 WEB_SELECTORS.price_class_patterns
```

按建议改 `xianyu_alert/web_parse.py` 里的 `WebSelectors`（**只改数据、不改逻辑**），
并把新页面结构粘进 `tests/test_webfetcher.py` 的 HTML 夹具做离线回归。

**如何确认已恢复**：日志变成 `网页解析 N 条（策略=…）` 且 N > 0。

## 10. 开机自启没生效 / 想关掉它

**先看状态**：

```bash
xianyu-alert autostart status
```

它会告诉你当前平台用的机制、文件在哪、是否已启用。

| 现象 | 原因 | 处置 |
|---|---|---|
| macOS 状态「已启用」但没启动 | launchctl 未加载（无 GUI 会话时常见） | 文件仍在，下次登录会生效；也可手动 `launchctl bootstrap gui/$(id -u) <plist>` |
| Linux 报 systemd 错误 | 环境没有 systemd（WSL1 / 容器） | 该环境请改用其它方式（cron、容器 restart 策略） |
| Windows 建了快捷方式但没自启 | 旧版本建在**桌面**而非启动文件夹 | 升级后执行 `xianyu-alert autostart enable` |
| 想彻底关掉 | — | `xianyu-alert autostart disable`（同时注销并删除文件） |

**退出行为**：崩溃会自动拉起，**主动退出不会**（正常退出后不会被反复拉起）。
