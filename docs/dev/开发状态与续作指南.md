## 3. v1.8.1 —— 源码级排查修复（2026-09-22）

### 3.1 P0 · Cookie 池会被静默清空（**已修**）

**根因链（双路径共有）**：

```
config.serialize_cookie_pool()      对 "cookie 为空" 的条目 → continue（整条丢弃）
        ↑
gui.config_to_form()      ← 把解密失败的条目 cookie 置空（明文）
MonitorService._read_pool_plaintext() ← 同上
```

→ **任何一次"保存配置"或"Cookie 池操作"都会把无法解密的条目永久删除**。
触发条件：密钥更换 / `secret.key` 未随数据迁移 —— 正是迁移场景的高危点。
注释写的是「保留为空并在对话框中提示」，实现却在删数据（**实现偏离设计意图**）。

**修法**：条目携带 `_raw_cipher`（原始密文）穿过整条链路，序列化时原样回写；
展示层如实报 `invalid_encrypt`，不再误报成「未配置」。
**反向验证**：复刻旧逻辑跑同一输入 → 旧逻辑输出 1 条（条目消失），新逻辑输出 2 条。

### 3.2 P1（3 处，**均已修**）

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| P1-1 | `parse_detail_sold_status` 对任意非 0 `itemStatus` 判 `False` | **在架商品被标"已售出"并从列表隐藏** | 收紧为只采信 `itemStatusStr` 文案白名单；数值仅 `==0` 判在架，非 0 无文案佐证 → `None` |

## 6. 关键机制（v1.8.2 新增，续作时必须理解）

### 6.1 Cookie 失效的三个层次（实测结论，方案文档核心）

同一份 Cookie 打**不同接口**，会报**不同的错** —— 这是分离故障层次的方法：

| 层 | 触发症状 | 严重度 | 恢复手段 |
|---|---|---|---|
| **L0 令牌层** | `FAIL_SYS_TOKEN_EXOIRED` | 轻 | **全自动**：服务端下发新 `_m_h5_tk`，重算签名重试即可 |
| **L1 会话层** | `FAIL_SYS_SESSION_EXPIRED` | 重 | 只能重新登录（数周~数月一次） |
| **L2 风控层** | `RGV587_ERROR::SM::被挤爆` | 中 | **重新登录无效**，只能降速/换账号/换出口 |

**实测证据（2026-09-24，NAS 生产实例）**：
- 搜索接口 → `RGV587_ERROR`（风控）；详情接口 → `FAIL_SYS_TOKEN_EXOIRED`（令牌）
  → **反证登录态仍然有效**，当时的真实处境是「L0 + L2」
- 令牌过期响应**同时下发** `_m_h5_tk` + `_m_h5_tk_enc`，均 `Max-Age=5400`
  → 证明**无感续期在服务端侧是通的**，缺口全在客户端

### 6.2 无感续期闭环（四步）

```
服务端下发新令牌 → _absorb_token 吸收（_tk + _enc 成对）
    → 重算签名重试该次请求（已实现，_search 的 round_index==0 分支）
    → 节流写盘（≥5 分钟一次，MonitorService._persist_refreshed_token）→ 重启不倒退
```

**配置热重载（关键，几乎零成本的同步机制）**：
`monitor_service._check_config_mtime()` 每轮开始前比对 `config.yaml` 的 mtime，
一变就重载并把新 `Config` 挂到运行中的 monitor。
→ **任何往 `config.yaml` 写 Cookie 的手段**（侧车容器 / 脚本 / 远程 CLI）都会**下一轮自动生效**，
主程序一行不用改。这是侧车方案能落地的地基。

### 6.3 实测校准的常量（**别再照抄旧文档的 24 小时**）

| 常量 | 值 | 依据 |
|---|---|---|
| `TOKEN_TTL_MS` | `90 * 60 * 1000`（90 分钟） | 实测响应 `Max-Age=5400` |
| `TOKEN_EXPIRING_SOON_MS` | `TOKEN_TTL_MS // 6`（15 分钟） | 按比例而非固定 1 小时 |
| 文案 | `token_ttl_text()` / `token_expiring_text()` | **动态渲染，禁止再写死小时数** |

> v1.8.2 前是硬编码 24 小时 → **误报"Cookie 正常"窗口长达 22.5 小时**。
> 当时"24 小时"散落在 4 个文件的字符串里，差点漏改 —— 故改成动态文案。

### 6.4 失败分层 → 正确的处置指引

`FetchError.kind` ∈ `token` / `session` / `risk` / `config` / `network` / `unknown`，
`monitor.py` 的 `_FETCH_FAILURE_HINTS` 按层输出建议。

> **判定顺序有坑（已修）**：风控标记里含宽泛的 `SM::`，原顺序会把
> `FAIL_SYS_SESSION_EXPIRED::SM::…` 误判成"该降速"。现改为 **session 优先**。
> 新增失败标记时务必复核顺序。

### 6.5 Playwright 持久化（免扫码刷新）

`acquire_via_playwright()` 从 `new_context()` 改为
`launch_persistent_context(user_data_dir=data_dir()/browser_profile)`：

- **profile 存在** → 静默模式（headless），打开一次站点即拿到新鲜令牌，**无需扫码**
- **profile 缺失** → 交互模式，需人工登录一次
- `headless=None` 时按 `profile_ready()` 自动判模式
- **前置校验必须有**：曾因"能 import playwright 但 profile 未建"而真的启动浏览器并等满 30 秒，
  把冒烟测试拖挂 → 加 `profile_ready()` 前置检查后变成**立即返回 409 + 可操作指引**

## 7. 验证体系（五层，**改完必跑**）

```bash
# 一键五层（默认对 127.0.0.1:8080；NAS 实例见下）
scripts/verify_all.sh --base http://10.0.0.26:8899

# 或分层单跑
python scripts/check_web_contract.py            # L1 契约静态比对
python scripts/e2e_web_smoke.py                 # L2 HTTP 冒烟（临时后端 + mock）
node scripts/e2e_web_dom.js                     # L3 DOM 端到端（jsdom）
python scripts/verify_web_deploy.py --base ...  # L4 部署验收（含静态资源 sha256）
node scripts/e2e_web_dom_live.js --base ...     # L5 live DOM（只读，对生产零写入）
```

| 层 | 抓什么 | 是否需要起服务 |
|---|---|---|
| L1 契约静态比对 | 前端调用的 URL/字段/通道 ↔ 后端源码 AST，**抓"对不上的名字"** | 否（最快） |
| L2 HTTP 冒烟 | 接口语义，可随便写数据 | 临时 uvicorn |
| L3 DOM 端到端 | **渲染期才暴露的问题** | 临时后端 + jsdom |
| L4 部署验收 | **镜像里是不是新前端**（静态资源逐字节哈希） | 已部署实例 |
| L5 live DOM | 对生产实例的只读断言（**★ 全程只发 GET**） | 已部署实例 |

**环境依赖**（脚本内已做回退，可用环境变量覆盖）：

| 变量 | 默认值 |
|---|---|
| `XY_PY` | `/Users/xxx/.workbuddy/binaries/python/envs/default/bin/python` |

## 9. 续作路线图

### P1 · 侧车容器（让 NAS 真正无人值守刷新 Cookie）

**为什么需要**：主容器是 alpine，Chromium 官方不支持 musl；体积会从 **31MB → ~1.5GB**。
且 NAS 上无人值守时，一旦 Cookie 失效就永久躺平。

**方案**（已设计完，未实施）：

```
[侧车] mcr.microsoft.com/playwright 官方镜像（glibc）
   │  挂载同一份 data/ 卷，定时/按需执行 cookie refresh
   │  写出新鲜的 config.yaml
   ▼
[主容器] xianyu-alert —— 靠已有的 mtime 热重载自动用上，零代码改动
```

要点：
- 共享卷 + mtime 热重载（**地基已就绪，见 §6.2**）
- 侧车需挂 `browser_profile` 目录持久化（否则每次都退化成人工扫码）
- 触发方式可选：定时（cron）/ 健康检查发现 `expired` 时唤醒 / 主容器 state 文件通知
- ⚠️ **首次登录仍需人工一次** —— 侧车消除的是"后续续期"，不是首次

### P2 · 其他可选项

| 项 | 说明 |
|---|---|
| 令牌落盘的更细粒度 | 当前节流 ≥5 分钟一次，可考虑"令牌变化即写"（需评估写盘频率） |
| 风控自适应降速 | 连续 `RGV587` 时自动拉大 `interval_seconds`（当前只给提示） |
| `token_ttl` 服务端漂移监控 | 若阿里调整 `Max-Age`，动态从响应头学习而非硬编码 |
| 「校验在架」取消响应速度 | 见 §8.2 #3，可按需改为可中断 |

## 11. 踩坑清单（续作前必读）

| # | 坑 | 教训 |
|---|---|---|
| 1 | **改共享常量前先扫测试** | TTL 一改，**7 个测试文件**里按 24h 写死的样本集体失准。正确做法：样本改成**相对常量计算**（`now - TOKEN_TTL_MS + …`） |
| 2 | **BSD grep 不支持 `\|` 作 OR** | macOS 自带 grep 会**静默返回无匹配**，让人误判"这个函数不存在"。用 `grep -E` 或 ripgrep |
| 3 | **`agent-browser` 不能判定"前端坏了"** | 其浏览器有持久缓存，曾报出"页面无样式、app.js 未执行"的假象。改用 **Playwright 直连复验**，并打印 `Object.keys(window.XY)` / `pageerror` / console error / 4xx 列表 |
| 4 | **`wait_until="networkidle"` 对 SSE 页面永远超时** | 页面上有 SSE 长连接 → 必须用 `wait_until="load"` |
| 5 | **pytest `tmp_path` 在受限沙盒不可用** | basetemp 落在 `/private/var/folders/...` 会被拒 → 测试改用 `tempfile.mkdtemp()` |
| 6 | **改既有语义前先查 `docs/` 依据** | 没有依据的旧断言可能只是"照实现反推"，不是契约。找到依据再改，并把理由写进测试注释 |
| 7 | **`docker compose` 必须带 `-p xianyu-alert`** | 目录名含中文，项目名推导会出问题 |
| 8 | **数据迁移必须带 `secret.key`** | 缺它 = 密文 Cookie 永久失效（曾因此触发 P0 数据丢失） |
| 9 | **静默/无人值守路径必须先做廉价前置校验** | 否则会真的启动浏览器等满超时（见 §6.5） |
| 10 | **探测第三方 API 凭证失效层次的方法** | 用**同一份凭证打不同接口**对比错误码；从响应 `Set-Cookie` 读 `Max-Age` 拿真实 TTL，**别信代码里的硬编码假设** |
