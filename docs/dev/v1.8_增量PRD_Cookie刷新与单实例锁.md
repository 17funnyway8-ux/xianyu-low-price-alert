## 2. 产品定义

### 2.1 产品目标（一句话 + 量化指标）

**一句话**：让 7×24 挂机用户在 Cookie 过期时「先知道、能快速恢复」，并杜绝多实例并发写库导致的数据库锁死/数据损坏。

**可量化指标**（v1.8.0 验收时衡量）：

| # | 指标 | 目标值 | 口径 |
|---|---|---|---|
| M1 | Cookie 过期提醒时效 | 过期后 **1 个检测周期内**（默认 ≤ 600s）推送提醒 | 配置了至少一个通知通道的前提；状态跃迁才提醒（去抖） |
| M2 | 刷新恢复耗时（自动化部分） | 校验 + Fernet 加密保存 + 回写 **< 30s** | 不计人工粘贴/登录时间 |
| M3 | 单实例锁拦截率 | 已运行实例存在时，新实例 **100%** 被拒绝并提示退出 | 覆盖 GUI（Tk/Qt）+ `cli run` + `cli once` |
| M4 | 异常退出恢复 | 进程崩溃/kill 后，新实例 **无需人工删锁** 即可立即启动 | OS 级文件锁自动释放 |
| M5 | Cookie 池过期项处置 | 池内含过期条目时，轮换 **100% 跳过过期项**（纯函数单测覆盖） | 不向 fetcher 注入已过期 Cookie |
| M6 | 回归 | **749 基线全绿** + 新增回归测试全绿 | 平台相关例外见 §4 备注 |

### 2.2 用户故事

1. **挂机 3 天提醒**：作为 Mac mini 7×24 挂机用户，当 `_m_h5_tk` 过期时，我希望工具通过 Bark/Server酱/邮件等已配置通道推送到我手机「Cookie 已过期」，我回家后在 GUI 点「一键刷新」粘贴新 Cookie、状态灯变绿、监测自动恢复，这样监测不再因 Cookie 静默失效而空转。
2. **过期前预警**：作为挂机用户，我希望 Cookie 剩余不足 1 小时时收到一次「即将过期」提醒，让我提前刷新，这样监测全程无中断。
3. **双开防护**：作为普通用户，我不小心双击了两次 exe，希望第二个窗口自动弹出「已有实例正在运行」并退出，第一个实例不受影响、数据库不被锁死。
4. **多账号池容错**：作为配置了多 Cookie 池的用户，其中一个账号过期后，我希望工具自动跳过它、继续用其余有效账号轮换，并提醒我「池中有 1 条已过期」，这样不会因单条过期导致整池抓取失败。
5. **cron 与 GUI 并存**：作为计划任务用户，我设了 `cli once` 每 10 分钟跑一次，当 GUI 正在挂机时，`once` 应提示「已有实例运行中」并退出，而不是和 GUI 抢写数据库。
6. **CLI 快捷刷新**：作为命令行用户，我希望用 `cli login`（粘贴/--cookie-string/playwright 三种模式）即完成刷新，刷新后工具校验 Cookie 有效才加密写回，避免把无效 Cookie 存进去。

## 3. 需求池

> 优先级：**P0** = 必须（本版本核心交付）；**P1** = 应该（增强体验，视排期决定）；**P2** = 可不做（明确不纳入）。

### 3.1 Cookie 自动刷新

#### 3.1.1 过期检测与提醒时机

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| C1 | 运行期周期检测 | P0 | `Monitor.run_forever` 每轮（或按 `cookie_check_interval_seconds`，默认每轮）对「本轮将使用的 Cookie」做过期检测。检测为纯本地时间戳解析（复用 `cookie_expiry_status`），无网络开销。 |
| C2 | 过期推送提醒 | P0 | 检测到 `expired`（含 `missing`/`no_token`/`invalid_encrypt`）时：① 记 warning 日志（现状）；② 通过全部已配置通知通道推送「Cookie 已过期，请刷新」提醒（含刷新指引文案）；③ **不打断**监测循环。 |
| C3 | 即将过期提醒 | P0 | 检测到 `expiring`（剩余 < 1h）时推送一次「即将过期」提醒，提前量可配置（默认沿用 `TOKEN_EXPIRING_SOON_MS`）。 |
| C4 | 提醒去抖 | P0 | 同一 Cookie 同一状态（expired/expiring/ok）**只在状态跃迁时提醒**，避免每轮/每小时轰炸；状态恢复 ok 后再次过期才重新提醒。去抖状态建议持久化到 SQLite `meta` 表（跨重启有效）。 |
| C5 | 无通知通道降级 | P1 | 未配置任何通知通道时，过期提醒仅落日志 + GUI 状态灯红色高亮 + 弹窗提示（GUI 在线时），不静默。 |
| C6 | 检测周期配置 | P1 | 新增 `monitor.cookie_check_interval_seconds`（默认 = 每轮检测；允许用户放宽到独立定时器）。 |

#### 3.1.2 刷新入口（GUI / CLI）

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| C7 | GUI 一键刷新入口 | P0 | Tk 与 Qt 两套 GUI：状态灯区域增加「一键刷新 Cookie」按钮，点击打开引导式刷新对话框（三步：① 打开浏览器登录说明 / ② 粘贴 Cookie 或 playwright 半自动提取 / ③ 校验并保存）。复用现有 `COOKIE_MANUAL_HELP`、`acquire_via_playwright`、`cookie_status` 校验。 |
| C8 | Cookie 管理对话框刷新能力 | P0 | 现有「Cookie 管理」对话框（Tk `on_manage_cookies` / Qt `CookieDialog`）内增加「刷新选中」：对池中单条或单值执行校验 → 保存 → 回写，刷新后健康列即时更新。 |
| C9 | CLI 刷新入口 | P0 | 复用 `cli login`（已有 --cookie-string / playwright / 粘贴三种模式）即完成刷新；增强：登录成功保存后**自动校验**（见 C11），并输出「已刷新并加密保存，可运行 once 验证」。文档明确「login = 首次登录 + 刷新」双重语义。 |
| C10 | CLI 状态查看 | P1 | 新增 `cli cookie status`（或 `cli login --check`）：只检测并打印单值 + 池内各条健康状态（不写入），便于脚本/ssh 远程巡检。 |

#### 3.1.3 多 Cookie 池过期项处置

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| C11 | 轮换跳过过期项 | P0 | `resolve_cookie_for_round` / `pool_enabled_cookies` 增强：池中 `expired`/`no_token`/`invalid_encrypt` 条目**不参与轮换**（仅用 ok/expiring 条目）；全部失效时回退单值 `monitor.cookies`（若有效），再失效则返回空并走既有抓取失败路径。 |
| C12 | 池过期汇总提醒 | P0 | 池中任一条目失效时推送一次汇总提醒（「池中有 N 条 Cookie 已过期/无效」），随 C2 去抖策略；单条明细在 GUI 健康列可见。 |
| C13 | 池过期条目标记 | P1 | GUI「Cookie 管理」对话框：过期条目行高亮（已有健康列），新增「自动停用过期项」/「一键剔除过期项」按钮（可写回 `enabled=false` 或删除，写盘前需用户确认）。 |

| 编号 | 需求 | 优先级 | 说明 |

| C18 | 刷新成功反馈 | P1 | 刷新成功后 GUI 弹窗/日志提示「Cookie 已更新并加密保存，下一轮将生效」，CLI 打印同样信息。 |

### 3.2 进程单实例锁

#### 3.2.1 锁的粒度

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| L1 | 一把全局进程锁 | P0 | 新增进程级单实例锁，**GUI（Tk/Qt）+ `cli run` + `cli once` 共用一把锁**（三者都会打开 SQLite 写库 / 跑监测循环，符合 README「不可同时运行」语义）。 |
| L2 | 锁的 key | P0 | 锁锚定 `paths.data_dir()`（默认 DB 路径 `state/xianyu_alert.db` 的锚定目录）→ 同一数据目录下只允许一个实例。 |
| L3 | `cli login` / `cli list` 不参与 | P1 | `login`（写 config.yaml、不写 SQLite）与 `list`（只读）默认**不参与**该锁：挂机场景下 login 需在 GUI 运行时可用（这正是刷新入口）。**风险**：GUI 内存态 config 可能与外部 login 修改冲突 → 配套 C22（GUI 配置变更检测），见待确认 Q7。 |
| L4 | 锁幂等 | P0 | 同一进程重复获取（如 `cli gui` 与 `run_gui.pyw` 叠加、入口与子模块都调用）必须幂等，不得自锁。 |

#### 3.2.2 已有实例时的行为

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| L5 | GUI 冲突提示 | P0 | GUI 启动时检测到已有实例 → 弹 messagebox「已有实例正在运行（PID xxx），请先关闭再启动」，退出码非 0；不阻塞、不抢锁。 |
| L6 | CLI 冲突提示 | P0 | `cli run/once` 检测到已有实例 → stderr 打印「已有实例运行中（PID xxx），请先退出再运行」，退出码（建议 2），不阻塞。 |
| L7 | 转发请求给已有实例 | P2 | 不做（如「请求已有实例立即跑一轮」需套接字 + 进程间协议，成本高收益低）；仅在待确认 Q9 中保留讨论。 |

#### 3.2.3 锁失效 / 异常退出处理

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| L8 | OS 级文件锁 | P0 | 采用 **OS 级文件锁**：POSIX（macOS/Linux）`fcntl.flock(fd, LOCK_EX|LOCK_NB)`；Windows `msvcrt.locking(fd, LK_NBLCK, 1)`。进程退出（含崩溃 / kill -9 / 断电）由 OS 自动释放——**无残留锁问题**，锁状态在打开的文件描述符上而非文件存在性。 |
| L9 | 锁文件位置 | P0 | `data_dir()/state/instance.lock`（与 DB 同目录，state 目录已存在；锁文件可残留为空文件，不构成占用）。 |
| L10 | 目录不存在容错 | P0 | 获取锁前确保父目录存在（复用 `paths` 语义）；锁获取失败（IO 异常）按「无法确认独占」处理：记 warning 并放行（不因锁模块故障阻断主流程），或按配置严格退出——默认放行 + 日志。 |

#### 3.2.4 跨平台实现

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| L11 | 新增 `singleton.py` 模块 | P0 | 新增 `xianyu_alert/singleton.py`：`acquire_instance_lock()` / `release_instance_lock()` / `is_running()`（只检测不持有）；平台分支在模块内封装，**零新增运行时依赖**（对齐项目哲学）。 |
| L12 | 接入点 | P0 | 在 `build/entry.py`、`cli.main()`（run/once/gui 分支）、`gui.main()` / `gui_qt.main()`、`run_gui.pyw` 统一接入：**确定 data_dir 后、打开 Storage/写库前**获取锁。 |
| L13 | macOS .app 双开 | P1 | macOS 双击 .app + LaunchAgent 自启同时触发时，第二个实例同样被锁拦截（OS 级锁天然覆盖，无需 Qt 单例机制）；Qt 侧可追加提示文案优化。 |

## 5. 不做什么（明确排除）

| # | 不做 | 原因与依据 |
|---|---|---|
| N1 | **全自动无感刷新**（无人工干预的自动重新登录） | 硬约束：闲鱼 mtop 需要登录 Cookie，登录必须经浏览器交互（扫码/短信/验证码）；`cookie.py::acquire_via_playwright` 明确 `headless=False` 等待用户登录（维护交接文档 §10.4：工具不自动重新登录）。自动模拟登录会显著触发风控（RGV587）且可能违反平台条款，账号存在封禁风险。 |
| N2 | **自动输入账号密码** | 凭据安全 + 风控双重风险；本项目 Cookie 用 Fernet 加密存储，明文密码自动化与本设计冲突。 |
| N3 | **验证码自动识别 / 打码服务** | 依赖第三方服务、安全性差、稳定性不可控；不属于本工具价值主张。 |
| N4 | **CDP 复用本机已登录浏览器（本期）** | 技术上可行（如 playwright `connect_over_cdp` 复用 Edge/Chrome 会话），但依赖本机浏览器已登录且会话存活、闲鱼可能识别自动化、跨平台行为不一致、调试成本高。**保留为未来方向评估**，本期不做（列入待确认 Q10）。 |
| N5 | **单实例锁的请求转发**（如「让已有实例立刻跑一轮」） | 需套接字 + 进程间协议，成本高收益低；本期只做「检测 → 提示退出」。 |
| N6 | **独立 daemon / 常驻后台服务改造** | 超出本期范围（维护交接文档 §10.5：GUI 关闭即停止监测）；单实例锁不改变进程模型。 |

**边界说明（做什么的度）**：本期 Cookie 刷新的交付形态 = 「检测过期 → 主动提醒（通知/日志/GUI）→ 引导式半自动刷新（GUI 一键 / CLI login）→ 校验 + Fernet 加密回写 → 池过期项自动跳过」。这是在不自动登录前提下能做到的最大程度。
